# Moonshine long dictation investigation

Baseline: `eb5e1dadfd9d6ceb2ebb78ca4f403d2718bddcf8`. Ticket branch: `codex/moonshine-long`. Investigation date: 2026-09-28.

## Decision and evidence

Leave segmentation, default settings, history and other recognition models unchanged. Source inspection establishes existing runtime segmentation and demonstrates backend failure/lifetime defects. It does not establish acceptable long-dictation accuracy or phone performance. The ticket remains open for the physical-phone baseline and affected device scenarios.

The [pinned runtime research](moonshine-runtime-segmentation-sources-2026-09-28.md) records primary sources and the cached 0.0.68 AAR identity. Its native VAD already completes speech segments while the stream remains active. Its configured maximum is not a measured, exact segment boundary. No additional VAD or long-dictation mode is justified by the available evidence.

The Android flow has separate stopping controls:

- Both Activity and IME use `RecognizerView` and `RecordingSession`. `AudioRecognizer.kt` creates WebRTC VAD at 16 kHz, using 480-sample frames. When automatic stopping is enabled, detected silence beyond the selected end-of-speech profile finishes recording. Moonshine's `LineCompleted` callback instead appends completed text and leaves the microphone running.
- `IS_VAD_ENABLED` defaults to true. `ENABLE_30S_LIMIT` defaults to false. Disabling automatic stopping and the optional duration limit already permits manual Stop for longer recordings. `RecognizerView.kt` also exposes pause-auto-stop while recording. Elapsed time does not switch recording modes.
- `RecordingSession.appendSamples` retains PCM and writes enabled audio history before feeding streaming recognition. The session's PCM buffer grows in 30-second increments when the limit is disabled. Moonshine has an unlimited feed channel. Runtime segmentation therefore does not establish bounded total app memory or prove that decoding keeps up. Two minutes of retained mono float PCM alone is 7,680,000 bytes, excluding allocation slack, queued chunks, model memory and copies.
- Live Moonshine uses `startStreaming`, `acceptAudio` and `finishStreaming`. History retranscription uses `transcribeWithoutStreaming`, so a history timing is not evidence of live segmentation behavior. S1 and Harper processing happen after the raw recognition result; measure them separately.

## Demonstrated corrections

1. Baseline worker `launch` plus `join` returned success after a fake engine emitted a partial and threw. The regression test failed with a null finalization exception. `async` plus `await` now propagates the failure with its original type and cause. Coroutine debug mode can copy an exception to recover its stack; tests allow that copy only when it retains the original failure. Kotlin documents propagation in its [exception handling API](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-coroutine-exception-handler/index.html).
2. Baseline `trySend` ignored rejected feeds, including feeds before start. Checked channel results now reject invalid feeds. The worker retains its failure explicitly because Stop can close the queue before the worker fails. Further feeds then preserve the original cause, even when the channel's close cause cannot be replaced. No error is classified as recoverable here.
3. A cancelled caller previously skipped engine release at `cancelAndJoin`. Non-cancellable cleanup now cancels the queue, joins the worker, then stops and releases the engine. A latch-controlled fake native feed verifies release ordering and discarded queued audio. [Coroutine cleanup documentation](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/with-context.html) supports the non-cancellable cleanup pattern.
4. In the actual pinned Java bytecode, `removeAllListeners` only clears listeners. A narrow subclass bridge invokes the protected 0.0.68 finalizer to release the default native stream and transcriber immediately. That implementation resets handles to -1, making subsequent successful finalization harmless. Failed construction also releases acquired handles while preserving the original load error. This is tied to the inspected version, not a promised upstream public API. Native release and reload still require Android execution checks.
5. Review identified that model selection followed by deletion of the old model can close an active runtime while full-clip transcription runs. A failing latch-controlled regression demonstrated release racing transcription. A shared monitor now serializes all native engine calls with release; late calls re-check engine availability inside that monitor. Worker cancellation/join stays outside it to avoid a lock/join deadlock.

The regression suite also checks cancellation and out-of-memory exception identity, finalization failure, repeated close, and a fresh independent backend after closing the old one. It retains the existing short-stream partial/final and full-clip transcription checks. SHARE-08 owns any bounded same-model replay in the session layer; this patch introduces none. Session cancellation and history code are unchanged.

## Physical-phone baseline procedure

Use the user's Galaxy S25 Ultra and the preparation/export steps in [Phone dictation test](../phone-performance-test.md). Record app revision, Android version, Moonshine Small/Medium, entry point, language, auto-stop profile, 30-second limit, backup/retention settings, cleanup settings, dictionary rules, charging state and temperature. Keep raw recordings and diagnostic archives out of Git.

1. Test each installed Moonshine variant in both IME and recognition Activity. Start with the normal short-message settings, including automatic stopping enabled and the actual duration-limit setting recorded. Read passage A from the phone guide, pause naturally and observe automatic stopping. Repeat three times, retaining failures. Repeat with manual Stop immediately after the last word.
2. Disable automatic stopping and the 30-second limit explicitly. With cleanup off, run approximately 30 seconds and at least 120 seconds of speech. At each duration include three separate conditions: natural pauses, a 5–10 second thinking pause followed by more speech, and uninterrupted speech. Use a prepared non-sensitive passage with numbered sentence markers to locate omitted or repeated boundary words. Keep speaking pace natural; record actual duration. Repeat each condition three times and record cold versus warm runs separately.
3. During every run, note partial updates before and after pauses and any delay in following current speech. At Stop, preserve the unedited raw recognition text and compare with the spoken passage. Check the final phrase, ordering, duplicate/missing words at internal segment boundaries, premature microphone termination and whether final output agrees with accumulated partials. Standard diagnostics exclude transcript text; retain this comparison separately with consent.
4. Measure Stop to `RECOGNITION_FINISHED` using matching session elapsed timestamps for raw recognition completion. `RECOGNITION_FINISHED.DURATION_MS` measures only post-stop finalization for live streaming, not total decode CPU cost. Record process CPU time with an Android profiler and sampled total PSS/native/Java memory before capture, at 30/60/120 seconds, after finalization and after closing/reopening the model. Report sampling cadence and overhead; sampled maxima are not proven peaks. Use profiling runs separate from the ordinary latency runs.
5. Restore normal short-message settings and repeat step 1. Test Cancel during capture and while Stop is finalizing, then start another dictation. With backups enabled, verify the cancelled recording remains recoverable under current retention rules and no cancelled text reaches the receiving app. With backups disabled, verify no recording is retained. Test repeated model load/close and switching variants, looking for crashes, unusable fresh instances or accumulating native memory.
6. If evaluating S1 rewriting, run a separate labeled block after the recognition-only baseline. Report S1 time and changes separately. Export standard diagnostics after each block; never silently enable transcript-inclusive diagnostics.
