# Diagnostics coverage audit, October 9, 2026

Audit for [#18](https://github.com/Today20092/voice-input/issues/18). Source baseline: `ad3b01debf2d08154fe952321b98fafeeb965568`, on `codex/parakeet-redux`. Runtime sources are unchanged from the earlier review at `44da59d`. This document separates source-verified behavior, existing tests, proposed corrections, and checks still pending. It is not a claim that diagnostics explain every possible failure.

## Findings and verification status

Standard diagnostics already provide a useful content-free event store, bounded asynchronous writer, stage timings, sampled resources, safe exception projection, and manually shared ZIP. Detailed mode already adds useful evidence. Do not replace these mechanisms or expand content permissions.

The highest-priority findings are outside that safe ZIP boundary: legacy native logging prints personal vocabulary; raw exception/native messages can enter Logcat and S1 records; transcript-bearing temporary/cache files do not all obey capture retention; and a transcript stage is labeled delivered before Android delivery succeeds. Additional gaps concern diagnostics failure isolation, collection provenance, asynchronous correlation, and the evidence needed to separate no-speech causes.

Source review is complete for the capture producers and artifact boundaries listed below. Runtime privacy verification is **not passed**. `adb devices` returned no attached devices. The attempted `:app:testDevDebugUnitTest :app:lintDevDebug` run failed before compilation, first on missing Gradle Groovy DSL cache metadata, then on `Unsupported class file major version 69` with Java 25. Android Studio's bundled runtime is also Java 25. No tests or lint passed in this audit run. Old XML/build outputs and historical September test results are not current verification. Detailed-mode overhead is **unmeasured**, not zero. The packaged scenarios and measurement protocol below remain required before closing #18.

Changes for this audit are documentation and issue-intake corrections only. Runtime fixes belong in focused follow-up tickets. No automatic uploads, dump collection, audio capture, or transcript permissions were added. The existing untracked audit/benchmark plans and recording scripts were preserved.

Temporary files, a ZIP during construction, failed deletions, and sensitive exports need separate accounting. ## Classification, correlation, ordering, and unavailable values

All S/D matrix rows inherit the S store and E export behavior above. Allowed technical data are enum events, numeric counters/timings, known model IDs, random local UUIDs, safe stack symbols, build/device model/SDK/ABI information, and individually enumerated settings. These can reveal device/configuration characteristics and approximate dictation lengths; they are content-free, not anonymous. Reporter notes are user-supplied sensitive text, limited to 4000 characters per field and previewed. T/H/X/B contain content and require their separate controls. Prohibited ordinary data include audio, transcripts/references, vocabulary entries, clipboard/surrounding text, receiving-app names, URLs, secrets, and identifying paths.

`DiagnosticSession` uses a random UUID and `SystemClock.elapsedRealtime` origin. `ELAPSED_MS`, `DURATION_MS`, `AUDIO_MS`, and `PROCESS_CPU_MS` are milliseconds. `timestampMs` is wall-clock time assigned when the writer records an event, not when the producer emitted it. CPU is cumulative process CPU time, not percentage. `PSS_KB`/`RSS_KB` are Android kilobytes; Java/native/available/storage metrics specify bytes. Memory is sampled, not exact model allocation or guaranteed peak. `STOP_REASON` uses the Kotlin enum ordinal, while Harper outcomes are integers interpreted in ZIP.summary. Both need schema documentation to survive enum changes.

The single writer preserves accepted enqueue order; concurrent producers do not imply native causal order. Resource metrics are taken when the queued task runs and lack session `ELAPSED_MS`. A session's terminal event can coexist with later delivery outcomes. Model-load and final-recognition starts survive later managed errors if flushed; startup/native process death can lose queued evidence. There is no persisted process-run UUID, event sequence, entry-point field, or link from standard session to S1 `reportId`; PROJECT drops that ID. Process exits are recovered on next main launch for API >=30, limited to 16 historical exits and deduplicated by exit timestamp. They have no direct session ID.

Environment/settings are snapshots at export time. A user changing models/languages/settings after a failure can make them misleading. `recognitionModelVersion` uses the catalog model, not a recorded per-session installed version. APP.settings enumerates backend, catalog model/version, VAD, duration limit/drain, keep-warm, cleanup/Harper/runtime, history and popup settings. It omits effective recognition language, legacy model selection/decoding, actual recognizer thread/runtime version, and other runtime-specific settings. A serial or full DataStore dump would not help and is prohibited.

API <29 omits thermal status; API <30 reports exit-history unsupported. Other sampling errors are counted as writer drops rather than represented as unavailable with a reason. S1 thermal can be null. Some download `BYTES` use expected size with unknown mapped to zero, so they do not establish transferred bytes or zero-size input. `CHARACTERS` counts Kotlin string length, not semantic words or Unicode graphemes. The archive has schema versions and basic unit guidance but no metric/enum dictionary, capture interval, policy transition timeline, persistent drop counter, or per-source omission count. It reports corrupt app JSON lines and writer/export-budget omissions; retention losses and silently skipped S1 records are not included in that number.

## Privacy-path review and failure isolation

E has an explicit entry allowlist and reprojects S1 twice. TZIP exercises malicious arbitrary entry names, transcript keys, raw native output, and unknown failure values. TSTORE tests unknown session/model strings and exception messages. This is adequate structural protection for normal standard producer writes and the combined archive; no broader data export is recommended.

Those tests use short `SECRET`/`private` fixtures, not an exhaustive realistic fixture set across every logger, native callback, policy/persistence error, copy report and share path. Do not treat them as a global no-leak proof. Android/third-party native behavior has not been captured in this audit.

Verified unsafe paths:

- `WhisperGGMLBackend.transcribe` passes `personalDictionary` as glossary. WhisperModel.run embeds it in a prompt, and `voiceinput.cpp:159` writes the prompt to AKLOGI. `defines.h` uses `#if 1` and Android Logcat macros. Model load also prints a filesystem path at line 66.
- AR/VIEW log full recognition Throwables; WhisperModel uses `stackTraceToString`; downloader/migration call `printStackTrace`. Parakeet's optional engine logger logs decode exceptions. PaymentCompleteActivity logs invalid `targetData`. Exception input can contain content, URLs, or paths; the safe STORE failure projection does not protect these other sinks.
- S1 JNI forwards raw llama error text to Logcat and a loader-errors list. CLEAN copies discovery errors/native metrics into S1 run records. S1.record persists those strings and Copy last report exposes the raw line; X includes raw records. PROJECT protects E only. The exact sensitive text from installed library failures remains a packaged verification task; arbitrary-message flow itself is source-verified.
- START can initialize legacy ACRA when build configuration enables it. Default is false absent crash-report properties. The audit did not read credential files or assert the deployed APK setting. ACRA is a separate upload-capable path; verify packaged configuration and explicit user consent before claiming all crash handling is local. Do not add another uploader.

AR transcript capture and most app event writes are best effort. However CLEAN.recordDiagnostic does discovery and resource measurement/building outside `runCatching { S1MiniDiagnostics.record(...) }`. A diagnostic construction/resource failure can escape after normalization and affect the dictation result. APP.sample catches measurement errors, but its caller still makes a metrics copy/enqueue outside that protection. Source review identifies the risky boundary; injected filesystem/resource/queue failures are needed to establish its full behavior. X UI.shareZip and transcript load/delete paths lack UI.perform's exception wrapper. These need narrowly scoped failure-isolation tests, not arbitrary catch-all changes to recognition semantics.

## Detailed-mode overhead measurement protocol

No connected device means no measured overhead result can be supplied. Do not substitute a host serialization microbenchmark or sample frequency for Android overhead.

Use the same packaged revision, device/Android version, installed model/configuration, charging/power state, route and sample input in each pair. Disable T and H to isolate diagnostics. Hold cleanup/Harper settings fixed. Record ambient/device thermal status and available storage; wait for comparable thermal conditions, alternate S-only and S+D order, and identify first versus warm loads explicitly. Run at least five paired short 10-second and long 60-second cases on one streaming and one final-only model; include an injected recoverable diagnostic/export failure and a cancellation case. Keep each detailed block under 30 minutes or record renewal explicitly.

Record individual start-to-first-audio, first-partial where applicable, stop-to-accepted-delivery, load and finalization times, process CPU delta, named PSS/native/Java samples with cadence, count/bytes written to diagnostic directories including temporary/prepared files, writer drops, and successful/failed delivery. Use an independent monotonic test harness for latency where possible; existing report timing alone can be biased by writer delays. Export after timing, separately measure export latency/size, and inspect privacy locally. Report median/range and paired absolute/relative deltas, workload/model order and unavailable measurements. No universal acceptable percentage or exact memory peak is assumed. If detail materially increases missed updates/drop rate or latency, investigate sampling/pruning overhead before adding more signals.

The actual D implementation prunes/checks segments on each accepted record and collects resources on the writer thread; the writer queue is bounded but CPU/IO cost is not measured. D's five-second live sampling and repeated partials can explain stalls better than S alone. History D sampling is at load/decode boundaries, not continuous. These are source-supported utility claims, not a performance pass.
